# 护工账号与老人负责关系

更新：2026-11-05。本轮按“取消老人账号端，由护工管理老人资料”调整。

## 当前使用方式

平台前端只有管理员与护工两类使用入口。注册页面统一创建护工账号（数据库角色沿用 `user`），无法自行注册为管理员。老人作为档案对象由护工管理，无需注册和登录。

1. 护工注册并登录。
2. 管理员进入“老人照护 → 护工账号与分配”，为老人选择负责护工，填写原因后保存；也可在档案详情中分配。
3. 护工进入“负责老人”，查看并编辑自己负责老人的姓名、性别、出生日期、入住信息、房间床位、照护安排、联系人、健康和照护要点。
4. 填写修改原因并保存。修改记录保留操作人、原因和前后内容，多人编辑时检查档案版本，冲突需重新加载核对。

一位护工可负责多位老人，一位老人可有多位护工。没有分配的账号看不到老人档案。护工不能修改负责人员，不能访问其他护工负责的档案，也不能进入知识库或 RAG 管理页。管理员原有全院管理功能保留。

## 老人端撤下与已有数据

- 前端不再提供“我的健康档案”“我的餐食”页面，原地址跳转首页。
- 管理员档案详情不再展示“老人登录账号”绑定区域。
- 旧老人身份在前端登录时会退出并提示改用护工账号；路由守卫也拒绝旧老人身份进入功能页面。
- 不删除原账号、档案、历史选餐或绑定数据。旧老人自助与账号绑定的后端接口、服务及数据表暂作兼容保留，本轮未完成后端接口下线；不能把前端入口撤下理解为这些接口已删除。
- 原工作人员账号直接作为护工账号继续使用；旧老人账号不自动升级为护工，避免误授工作人员权限。
- 护工六个 Agent 提问页面沿用模型语音输入，服务端语音权限同步调整为护工。

本轮不新增数据库表或迁移，重启后端并刷新前端即可使用。

## 接口与后续工作

`GET /api/auth/caregivers` 仅管理员可获取护工列表、脱敏手机号及负责人数。`PUT /api/residents/{id}/assignments` 仅管理员可分配；`PUT /api/residents/{id}` 允许管理员与当前负责护工编辑，护工不能改变人员列表。原照护字段专用接口继续保留。

本轮先实现账户和老人资料管理效果。管理员餐食编排、发布和厨房汇总保留；老人档案自动注入 Agent、跨 Agent 协同调度尚未实现，需要按后续业务升级衔接。

自动测试覆盖注册不能提权、负责范围隔离、完整资料修改留痕、护工不可重新分配人员、版本冲突、撤销后的权限收回、前端旧老人身份拦截，以及语音输入权限。实际页面交互仍需本地验收。

## 护工侧栏布局

护工侧栏参考魔搭社区个人中心，采用顶部头像、姓名和身份区，下方排列业务菜单的布局，沿用项目浅色蓝色主题。当前仅展示“工作概览”“负责老人”和退出登录；老人详情页仍高亮负责老人。窄屏显示图标导航。原六个 Agent 的页面、路由与代码保留，暂从护工侧栏隐藏，管理员导航保持原样。

## 每位老人的每日餐食

在老人列表的“查看档案”旁点击“每日餐食”。页面显示当前老人姓名，可选择周次、切换周一至周日，查看已发布菜单中的早餐、午餐、晚餐并代为选餐。已选套餐会标记，截止前可以改选或重新确认，沿用选餐版本检查。

护工仅能管理当前负责老人的餐食，管理员可管理全院老人；撤销负责关系后立即失去餐食读写权限。确认套餐沿用原选餐记录，计入原有厨房汇总，操作记录包含实际护工账号。过敏、禁用食材、质地、标签、份数和截止时间规则保持生效，不能通过代选绕过。饮食资料未核实或档案变化时只能查看菜单，需管理员先在“饮食需求”核实再确认套餐。没有发布菜单时显示未发布提示。

该页面管理老人每餐的套餐选择；全院周菜单的菜品编辑、智能生成和发布仍由管理员在“每周餐食管理”完成。
