# 护工账号与老人负责关系

更新：2026-11-12。现行六岗位职责见[职责与入口收敛说明](../02-Agent设计/六岗位职责与入口收敛说明.md)。

1. 员工申请护工岗位，由院长核实开通。
2. **护理部**进入“护工账号与分配”，从已开通护工中选择老人负责人员；也可在老人档案中调整。院长不分配老人。
3. 护理部负责建档和修改，修改填写原因并检查版本。医务室核实结构化医护资料。
4. 护工进入“负责老人”，只能查看当前负责对象；不能修改档案或负责人员。
5. 护工从执行清单确认完成、打卡或上报异常。餐食只读，调整须进入“换餐校验”，经规则校验、食堂批准及备餐确认再执行。

一位护工可负责多位老人，一位老人可有多位护工。撤销负责关系后，接口立即收回该老人访问与执行权限。护理部资质过期时不能建档、分配或审核照护事项。

护理部独占 `GET /api/auth/caregivers`、建档、档案写入和 `PUT /api/residents/{id}/assignments`。院长不能通过地址或 API 绕过限制。护理部只管理已开通护工的负责关系，注册审核和账号启停仍归院长。

旧老人账号端、原六类咨询入口及自助绑定接口从正常产品撤下；历史资料和数据保留。每日餐食页面可查看历史已发布周菜单，不直接改写原选餐记录。新配餐和换餐执行单与历史菜单不自动同步。

本轮只调整入口及权限，无新增迁移；启动前仍需完成既有 `alembic upgrade head`。真实数据库、模型和页面交互应在本机验收。

## 五名护工各负责四位样例老人（2026-11-14）

在 `agent_env` 的 `backend` 目录执行：

```bash
python -m scripts.setup_caregivers --five-by-four --apply
```

省略 `--apply` 仅预览、不保存。前提是20位原样例001至020都存在且在院，旧021至100已经缩减；不足时脚本提示先运行 `python -m scripts.seed_residents --resize-to-20`，不擅自清理业务记录。

此命令只重设20位虚构样例的负责关系，每位老人仅分配给该组指定的一位护工，留下变更原因和前后记录。其他老人、其他账号及密码不删除。重复执行不重复创建或修改已经一致的负责关系。发生分配变化的档案版本会增加，既有医护资料或草稿可能需专业人员重新核实。网页日常分配权限仍归护理部；本脚本是由院长身份留痕的一次性本地初始化工具。
