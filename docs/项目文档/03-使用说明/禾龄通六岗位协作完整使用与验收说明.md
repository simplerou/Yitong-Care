## 1. 本轮交付与边界

本轮新增六岗位协作工作台、Supervisor 与岗位子图、独立校验服务、图谱事实导入、人工草稿确认、执行反馈、排班打卡、代码核薪、修正台账、药品说明书引用定位和部署配置。原档案、护工分配、周菜单、每日套餐、厨房汇总、旧咨询和 RAG 不删除。

代码验收与真实业务启用是两回事。自动测试使用 SQLite 和虚构事实，独立 HTTP 服务使用测试传输验证；MySQL 迁移离线 SQL 已编译。当前工具环境不能连接本机 MySQL，也没有已配置的 Neo4j，不能宣称真实数据库迁移、Neo4j 联调、容器部署或临床资料验证已经完成。

默认不使用虚构事实替代真实证据。正式图谱需要有资质人员核实并导入。不得根据演示剂量、营养目标、药品或规则指导真实老人。

## 2. 角色与工作台

| 数据库角色 | 岗位 | 业务入口 |
| --- | --- | --- |
| admin | 院长 / 原管理员 | 审批、看板、岗位资质、知识库、台账、审计及原全院管理 |
| medical | 医务室 | 医护资料核实、说明书、用药草稿、执行清单 |
| kitchen | 食堂 | 脱敏约束、目录与食谱参考、一日配餐、换餐审批、备餐确认 |
| nursing | 护理部 | 护工排班、上报审核、清单、修正跟进 |
| finance | 财务部 | 工时只读、核薪草稿、代码金额与工资说明 |
| user | 护工 | 负责老人、每日套餐、执行、打卡、观察上报、换餐申请 |

公开注册改为员工申请五类岗位，审核前只能查看申请状态；院长在“注册审核”核实后开通。新账号由注册审核确认岗位；已开通账号状态在注册审核管理，岗位与资质旧标签已撤下，详见[注册审核说明](员工注册与岗位审核说明.md)。医务室和护理部必须登记资质/任职核实记录及有效期；过期自动阻断专业操作。角色变更删除已有登录会话，需重新登录；系统保护最后一位院长账号不被撤销。

网关每次请求和重要工具边界重查账号、角色、有效资质与工具白名单，不接收模型指定的账号。护工目标按当前负责关系核对，未知对象和无权对象对外统一“不存在或无权”；内部日志分别记录缺失与越权原因。旧岗位的草稿不会因为所有者角色改变而继续暴露给新岗位。

## 3. 配置与启动

沿用现有 `agent_env`。在 `backend` 目录：

```bash
python -m pip install -e '.[dev]'
python -m scripts.prepare_collaboration
python -m scripts.check_db
alembic upgrade head
```

准备脚本只补缺失的内部校验配置；内部服务令牌已由随机数产生，不在终端输出，也不提交 Git。原有 MySQL、Qwen、Embedding、Tavily、ASR 和 HowToCook 密钥不修改。

## 4. 图事实与独立校验

校验服务不依赖大模型或主业务数据库。主 API 在授权后提供最小必要的结构化资料，校验服务内部查询 Neo4j，再用 Decimal 计算剂量、每日能量/蛋白/钠并判定过敏、重复活性成分、多重用药、疾病禁忌与食药冲突。

图谱包含 Drug、Food、Ingredient、Allergen、Disease、ContraindicationRule、Evidence、Role、BusinessDomain 和版本节点。查询使用固定参数化 Cypher，Agent没有任意图查询工具。成分冲突路径与证据绑定到草稿校验结果中，审批前重新取得图版本和事实哈希。药品证据必须有条号、原文位置、生效日期；正式事实还必须有来源URL，食物也必须有营养证据。营养数值按每100克计，药品剂量单位为mg。

事实清单格式见 `backend/validation_service/manifest.py`，虚构完整样例见本说明目录的 `禾龄通虚构图谱样例.json`。

```bash
# 只检查清单结构，不写数据库
python -m scripts.import_validation_graph /path/to/reviewed-facts.json
# 确认专业核实后写入并发布新版本
python -m scripts.import_validation_graph /path/to/reviewed-facts.json --apply --reviewer '核实责任人'
```

同版本内容不可覆盖，变更应使用新版本。图查询、认证、证据完整性或服务可用性检查失败时，不允许生成草稿。未知药品、食物、疾病或过敏原不当作“无风险”。

MCP可选入口：`python -m validation_service.mcp_server`，使用stdio，只暴露用药与营养校验，不暴露Cypher。主业务默认通过带独立令牌的HTTP调用相同规则逻辑。HowToCook继续使用原MCP适配器，食谱仅供参考，未核实的食物不会直接进入图谱配餐草稿。

## 5. 用药闭环

1. 院长授权医务室和有效资质；为护工分配老人。
2. 医务室进入“医护资料核实”，选择老人并读取，明确核实过敏、疾病、在用药、个体一日营养目标和专业依据。原自由文本不会自动当作已核实结构化信息。
3. 医务室读取药品目录，输入拟建议的药品、单次mg、每日次数和专业依据。
4. Supervisor通过网关后转交医务室子图，查证说明书，先校验，再由Qwen整理说明，再次复校，保存待确认草稿。
5. 院长在审批台核对方案、原始建议、人工修改、引用、规则版本和轨迹。3级风险必须填写核对意见。
6. 审批重新检查作者岗位与资质、草稿时效及版本、源资料指纹、规则与图事实版本。批准后形成执行单并更新结构化在用药记录。
7. 当前负责护工读取对应老人的执行单；执行前再次复核资料和规则，完成后记录实际执行说明。

这里的输入为专业人员建议，AI不自主开药、改剂量或直接执行。模型说明与结构化方案分开存储，不能覆盖代码结论。

## 6. 原文检索

管理员先在用药安全知识库上传说明书、切块及向量化，再到“药品原文定位”绑定药品标识、知识块编号、条号及有效期。读取时核对文档与切块哈希及字符范围，原文变化后旧绑定失效。

`GET /api/operations/drug-retrieval/{drug_id}`支持 query、category、on_date 和 hybrid。先筛选药品、类别和有效日期，再把允许的chunk集合交给FAISS + BM25 + RRF，不做全库召回后简单过滤。输出强制包含条号、原文位置和引用。无向量结果时可使用绑定范围内的BM25引用；没有有效原文时不补造引用。图事实中的有效说明书证据仍独立用于规则阈值判断。

原20万向量容量保护、不可变索引文件、原子发布、校验哈希和版本热加载保留。新增功能没有替换已有检索算法。

## 7. 食堂与护工换餐闭环

食堂“获取全院脱敏约束”由服务端收集已核实结构化资料，校验服务返回规则结论并建立短期凭证。食堂只见人数、规则版本和过敏约束，不见老人及药品标识，不与医务室Agent互调。未核实资料或凭证过期会阻断配餐，不能将资料未知当作没有禁忌。

食堂先选择服务日期，再从已核实目录输入一日完整食物总量；系统按每位老人的一日目标检查营养及冲突。配餐草稿经院长确认生成食堂执行单。这里是“一日方案”，不能用单餐数量去比较整日目标。

护工换餐：

```text
选择负责老人 → 输入完整一日替换方案及原因 → 代码校验
    → 有冲突则拦截，不生成草稿
    → 无冲突生成换餐申请 → 食堂核对并批准
    → 食堂仅收到匿名备餐单 → 食堂确认备餐
    → 护工收到带老人姓名的发放执行单 → 复验并确认完成
```

原“每日餐食”继续展示已发布周菜单。未启用结构化医护校验的历史业务沿用人工核实、截止时间和份数检查；一旦医务室建立结构化档案，旧选餐写入口会阻断并引导到岗位协作换餐，防止绕过食药冲突校验。医护核实或批准用药会更新老人档案版本，原选餐会进入待核对，不能继续当作有效备餐依据。新协作配餐/换餐单不会越权改写已发布周菜单；两类业务共享老人负责关系，但用不同单据清晰留痕。

## 8. 护理、财务与上报

护理部提交未来班次、护工、小时费率。代码拒绝已过去、超过12小时、与现有班次或本草稿重叠的排班。院长批准才生成正式班次，审批时锁定护工账号再次检查并发重叠。

护工只看到自己的班次，签到窗口为上班前30分钟至班次结束；必须先签到后签退，过迟签退转人工核实。操作幂等，不重复打卡。

财务只读排班及实际打卡，按“打卡与排班交集秒数 ÷ 3600 × 该班小时费率”逐班四舍五入至分，再汇总月金额，字符串保存货币精度。缺失打卡单列待补，未视为0；不含税、社保、加班费等尚未核实的人事政策。财务不能创建/修改排班，核薪草稿经院长确认，不自动转账。

护工上报日常或紧急观察交护理部审核。紧急情况须同时现场联系医护，不能等待网页审批代替应急处置。

## 9. 人工确认与修正回流

草稿30分钟内有效；脱敏凭证同为30分钟。未批准前不生成执行单。批准/退回检查草稿版本，成功的重复确认幂等。高风险用药和紧急上报为3级，配餐/排班/核薪为2级，日常观察为1级。不能审批自己提交的单据。

作者修改待确认草稿时必须填写依据、原因标签和改进方向：规则、Agent或培训。系统保留原建议、修改前后和最终确认，不把人工覆盖算成原建议采纳。院长可登记闭环说明；看板另列已记录只读工具的成功/失败及成功率，不含网关拒绝和无法写入审计的数据库故障。看板统计近7天、近30天、原样采纳和待闭环修正，无样本时返回未知。

待确认状态由MySQL持久化，是可恢复的人工作业边界；没有将进程内LangGraph状态误称为跨进程检查点持久化。LangGraph组织Supervisor与独立岗位子图，审批从持久化草稿重新鉴权和复校后继续业务执行。工具调用预算180秒，外部校验单次最多20秒；模型输出格式修正最多一次，不无限循环。

## 10. 验收顺序

建议先在隔离演示数据库验收，不在真实老人资料上填虚构药品。

1. 院长创建/授权五类业务账号，检查医务室/护理部资质有效期；反向验证护工不能自行提权。
2. 准备虚构老人并分配护工，核实结构化资料。食堂读取脱敏约束时检查无老人和药品标识。
3. 用药合规输入→草稿→高风险意见→院长批准→执行单→护工完成。
4. 超剂量、重复活性成分、过敏、食药冲突分别验证不产生草稿或执行单。
5. 同一草稿重复批准不重复写；过期、源资料变化、规则版本变化、作者岗位/资质变化均阻断审批。
6. 依次完成换餐申请→食堂备餐→护工发放，检查不能跳过备餐或查看他人老人。
7. 护理排班→批准→本人打卡→财务核薪→院长确认，验证财务不能改排班。
8. 修改草稿并选择规则/Agent/培训，批准后看台账和采纳率，再填写闭环说明。
9. 关闭校验服务、撤销资质或换护工，验证失败时没有未经批准的业务写入。
10. 用前后端测试和固定保留集复测，不用虚构数据推导简历历史指标。

## 11. 容器部署

仓库根目录的compose栈创建独立MySQL、Neo4j、校验服务、迁移任务、API和Web，不使用宿主机原数据库卷。配置 `COMPOSE_MYSQL_PASSWORD / MYSQL_ROOT_PASSWORD / NEO4J_PASSWORD / VALIDATION_SERVICE_TOKEN` 后：

```bash
docker compose --env-file backend/.env up --build -d
docker compose exec api python -m scripts.setup_admin
# 导入经过核实的事实后才能使用正式敏感草稿功能。
```

浏览器访问本地8080端口；Neo4j浏览器仅绑定本机7474，校验服务不发布外部端口。生产还需设置HTTPS、备份、监控、网络隔离和正式资质/事实维护流程；本轮没有执行公网发布。

最终自动化验证（2026-11-12）：后端610项通过，前端97项通过，生产构建通过，固定虚构规则8例及单独保留集4例通过。真实MySQL/Neo4j及浏览器点击验收仍以本地联调为准。
