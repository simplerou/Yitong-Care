# 智能周菜单生成说明

更新日期：2026-11-03。[返回文档导航](../README.md) · [每周餐食与选餐](每周餐食与老人选餐使用说明.md)

## 1. 使用流程

管理员进入“院内餐食 → 每周餐食管理 → 周菜单”，先读取目标周次，在“智能生成本周菜单”填写约束，再点击生成。

流程为：汇总已核实饮食需求 → LangGraph按天编排 → Qwen生成一天三餐 → 程序检查并最多修正一次 → 汇总七天草稿 → 按数据库最新资料逐位检查 → 管理员人工核对 → 显式保存 → 再次检查覆盖 → 管理员发布 → 老人本人选餐 → 厨房汇总。

生成只返回页面草稿并记录一次预览审计，不创建或更新正式周菜单，不调用发布接口，不修改老人档案或饮食资料。失败不使用固定参考模板冒充AI结果，也不替换原草稿。

## 2. 模型与配置

复用现有 `LLM_BASE_URL`、`LLM_API_KEY`、`LLM_MODEL`，无需另填一套Agent密钥。未配置、超时、额度或服务错误均明确反馈，不回退为假生成。调用链不使用Embedding或Tavily，不宣称查阅了外部临床资料。

新增编排为 `app/agents/menu_planner.py`，独立于原有膳食营养师聊天流程；原有膳食营养师不在本次升级范围。老人餐食页面的对话式解释助手也尚未实现。

本次不增加数据库表，使用已有餐食审计表；前提是已完成迁移0016。如餐食基础表尚未创建，先在backend中执行 `alembic upgrade head`。更新后重启后端、刷新前端。

## 3. 发送给模型的内容

后端只根据在院、人工核实且仍与当前档案版本一致的资料建立饮食条件组合：明确过敏原、禁用食材、要求标签、允许质地及每组人数。保留同一老人多个条件的组合，不把边际统计误当作个人约束。

不主动发送数据库老人ID、档案编号、姓名、联系电话、位置、完整病史、自由健康备注和核对来源。原始未核实资料不交模型猜测，只汇总待核实人数。独立账号和私人对话不作为生成输入。

按需参考上周同一天已发布菜品及本周已生成的菜品，减少重复；不发送上周备注中的个人信息。厨房说明、条件词项等均是数据，不能成为改变生成规则的指令；管理员也不应在厨房或预算说明中填入个人身份信息。

没有在院档案时要求先建档。有未核实资料时，默认拒绝生成，除非管理员明确确认“仅生成待审核参考草稿”；未知资料绝不视为无风险。匿名条件组合超过100种时拒绝省略需求，提示人工分组规划。

## 4. 管理员可填写的约束

| 项目 | 作用 |
| --- | --- |
| 每餐方案数量 | 2、3或4套完整餐食 |
| 可采购食材 | 非空时约束全部食材和配料必须使用清单中的原词项；生成结果越界会被拒绝 |
| 厨房制作条件 | 例如以蒸炖为主；供模型参考，仍须人工核实可执行性 |
| 时令偏好 | 例如秋冬季；不作为医学条件 |
| 预算/采购文字 | 仅用于参考，没有价格库，不代表预算核算通过 |
| 每套供应份数 | 由服务端设置；留空按在院人数给出待核实供应上限，不让模型虚构库存 |
| 参考上周轮换 | 将上周同一天菜品作为减少重复的参考；特殊饮食覆盖优先 |

截止时间沿用目标草稿中已设置的时间，没有现有草稿则使用原默认早餐06:00、午餐10:00、晚餐16:00。模型不能自行更改日期、版本、ID、供应份数或发布状态。

## 5. 检查与修正

每天必须有不重复的三餐，方案数及字段满足严格结构；七天合并后再次验证21个餐次及服务端生成的唯一ID。检查采购清单、允许标签、明确禁忌、质地与条件组合覆盖，拦截已知禁忌词项在菜名出现但未在食材/过敏原中声明的明显矛盾。

不接受疗效保证、虚构精确营养或份量数据。没有接入食物成分、价格、配方数据库，程序无法证明临床营养、预算或实际制作符合要求；词项和规则检查不能替代专业审核。

结构或厨房约束经一次修正仍不通过时，整周生成失败，保留原菜单。条件组合覆盖经一次修正仍有缺项时，可以返回未发布草稿，明确列出缺失的老人/餐次供管理员补替代餐；原有发布检查仍会阻止未覆盖的已核实需求。

生成后重新读取数据库：菜单版本或状态变化则返回冲突；老人资料变化则按新资料重新检查并显示提醒。最后的保存及发布仍使用现有版本校验和新鲜覆盖检查，不把生成时通过当成永久有效。

与上周相同的菜品组合及本周重复会统计提示，不强行删除特殊饮食所需的稳定方案。每周可以不同，不承诺所有菜品永不重复，也不把改方案名称当成新菜。

## 6. 时间和调用预算

采用请求内LangGraph，正常每周7次模型调用，每天最多修正1次，整周最多14次；网络/服务超时不会不断重试。每次最多4500输出token，请求超时沿用已有模型设置。页面生成请求最多等待15分钟，可能需要数分钟。

当前非后台队列，不提供恢复生成或服务端取消功能，离开页面可能丢失返回草稿，不能因此认定服务端任务已取消。生成期间不持有数据库读事务和菜单锁；不会因等待时长而自动发布。

## 7. 接口与留痕

POST `/api/meals/generate`，仅管理员。

请求包含目标周一、当前菜单版本、方案数、采购清单、厨房/预算/时令说明、供应份数、轮换与待核实确认开关。请求不接收老人身份名单或发布状态。

返回 `menu`（未保存草稿）、最新 `coverage`、人数摘要、警告、重复情况、模型名称、调用指标及明确的 `saved=false`、`published=false`。成功预览在 `meal_change` 记录生成周次、操作者、人数、检查计数及调用指标；不保存模型提示词或完整患者资料。

## 8. 测试与实际验收

后端545项测试、前端81项测试（77项Vitest、4项Node）及TypeScript/Vite构建通过。新增覆盖匿名汇总、组合人数、上下游权限、21餐完整性、生成不保存不发布、7～14次调用上限、采购越界、修正失败、覆盖缺项、原菜单保护、版本冲突、生成期间资料变化、上周参考和明显食材矛盾。

测试采用模拟模型输出，没有宣称已完成真实Qwen周菜单生成或本机MySQL、浏览器视觉验收。本轮没有运行真实模型付费全周评测；现有模型网络与数据库可用性需在用户环境实际验证。

建议先用一位虚构老人核实饮食资料，选择未发布目标周生成，检查菜品和警告；保存后再次覆盖检查再发布，切换老人账号选餐。不能把100份虚构资料批量假定为真实已核实健康状况。

## 2026-11-03：校验误拦与失败诊断修正

用户使用每餐2套、秋冬季、少油少盐蒸炖为主、供应10份、采购清单留空的设置，在第3天收到笼统错误。旧版未保存原始候选，不能追溯并断言实际触发项；空采购清单不会触发清单越界检查。

已修复可复现的问题：模型附加但未核实的通用标签从正式tags中移除，不再作为整周失败的原因；明确的中文餐次和质地可转换到系统值；否定性的“不保证疗效”说明不再误当正向承诺。未知质地、过敏字段缺失、禁用食材、必需标签缺失和正向疗效保证等检查保留，不自动补写任何安全条件。

失败消息现显示具体餐次/方案/字段及原因，原草稿不被替换。新的失败以600文件权限保存至 `backend/var/diagnostics/menu_planner/menu-*.json`，包含失败当天候选、检查项、匿名条件及完成天数，不保存模型密钥或原始老人身份档案。该目录不会提交Git。

重启后端后可按原设置重试，无新增迁移。若仍失败，在backend目录运行：

```bash
python -m scripts.inspect_menu_failure
```

加 `--candidate` 可查看失败候选。脚本只读本地诊断，不访问MySQL、不调用模型或搜索、不修改菜单，不产生新的生成费用。旧版未留存的失败无法由此恢复。

本轮完整回归548项、前端构建通过；新增规范化、未补造安全字段、明确原因、诊断文件隐私与权限用例使用模拟模型验证，真实生成仍需用户环境验收。


### 模型分工配置（2026-11-03）

通用 Agent 的理解、回答、生成和模型复核使用 `LLM_MODEL=qwen-plus-2025-12-01`；智能每周菜单生成使用独立的 `MENU_LLM_MODEL=qwen-plus-2025-07-14`。两者共用原有 `LLM_BASE_URL` 和 `LLM_API_KEY`。菜单模型配置留空时沿用通用模型。向量模型保持不变。修改 `backend/.env` 后需重启后端；实际模型访问权限以供应商响应为准。


### 食材重复导致生成中断修复（2026-11-03）

诊断记录确认模型在同一方案中重复列出“鸡蛋”，修正调用也未消除重复。现对生成结果的食材列表去除首尾空白并按原顺序去重，不新增或推断食材。空条目、超长条目、采购范围和饮食安全校验继续保留。提示词增加食材不得重复的约束。原失败记录两次输出经离线规范化后均通过结构校验；相关测试16项通过。未重新调用模型或修改已保存菜单。


### 菜品丰富度与轮换（2026-11-03）

原先方案只需一项菜品，重复统计仅比较整套餐食组合，现新增早餐至少3项、午晚餐至少4项的生成目标（均含主食）。按去除首尾空白后的具体菜名检查，除明确列出的基础主食外，同名菜品全周超过2次提示调整。发现不足或重复时触发一次修正，与原安全修正共用一次机会；仍未达到目标则返回提醒，不因多样性目标阻断生成。饮食条件覆盖优先，允许必要的特殊餐重复。此检查不识别菜名同义词、食物类别和实际营养结构，仍需人工核实，不承诺每天绝不重复。每餐可选套餐数量仍由2～4套配置决定。
