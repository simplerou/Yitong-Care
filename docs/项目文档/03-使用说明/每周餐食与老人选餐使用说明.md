# 每周餐食与老人选餐使用说明

更新日期：2026-11-03。[返回文档导航](../README.md) · [老人账号绑定](老人账号与档案绑定说明.md)

## 1. 当前交付

已实现周菜单草稿、全院饮食需求核对、覆盖检查、人工发布、老人本人选餐和厨房汇总。管理员维护一周七天早餐/午餐/晚餐，共21个餐次；每餐可安排1～8套完整餐食方案，每套列明具体菜品。首版选一套完整餐食，不是自由拼盘，也不自动生成治疗食谱。

独立膳食营养师 Agent 保持原有功能，没有接入本餐食业务；管理员菜单编排页已增加调用现有Qwen的智能生成入口，不调用联网搜索。详见[智能周菜单生成说明](智能周菜单生成说明.md)。老人可通过绑定账号选择，工作人员代选、紧急加餐、配送及实际进食登记留待后续。

## 2. 启用

在 `Yitong Care/backend` 下执行：

```bash
conda activate agent_env
alembic upgrade head
```

迁移0016新增 `weekly_menu`（每周菜单）、`meal_profile`（核实饮食要求）、`meal_selection`（选餐记录）、`meal_change`（操作留痕），依赖账号绑定迁移0015。之后重启后端，刷新前端。

本环境无法连接用户本机MySQL，助手尝试迁移被工具环境拒绝；实际建表和本机页面验收尚需执行上述步骤。已完成SQLite回归和MySQL离线迁移SQL生成，不等于真实MySQL迁移成功。

## 3. 管理员操作顺序

1. 先建立老人档案、绑定老人账号。
2. 左侧“院内餐食 → 每周餐食管理”，打开“饮食需求”。列表汇总所有在院老人的过敏、健康与饮食原始记录。
3. 选择老人，根据已核实资料登记过敏状态、明确过敏原、禁止食材、必须满足的饮食标签、允许质地、核对来源和备注。只有人工核实且过敏状态不是未知时，资料才可用于自助选餐。不能仅凭疾病名称自动判断，空记录不能当作无风险。
4. 打开“周菜单”，选择周次并读取，系统定位到周一。按每天三餐安排完整方案：名称、菜品、全部食材和调味配料、过敏原、饮食标签、质地、供应份数、说明和截止时间。
5. 可以“智能生成本周菜单”，也保留“填入参考草稿”或“复制上一周后调整”。智能生成结果尚未保存/发布，需人工核对；固定参考草稿不属于AI生成。参考菜单会按周轮换部分搭配，不代表专业营养方案；管理员必须补全并核对实际食材、调味和制作方法。复制保留为草稿，产生独立方案ID，不修改历史菜单。
6. 保存整周草稿，再“检查全院覆盖”。已核实老人在任一餐缺少匹配方案时不能发布，需先补替代餐。
7. 如果仍有待核实老人，界面列出名单。管理员可明确确认知晓后发布，但这些老人仅能查看菜单，不能自助确认选餐。发布不代表全院饮食资料已经核实。
8. 核对后发布。已发布菜单冻结，避免已有选餐对应菜品被静默改动；下一周创建或复制新菜单。当前不提供发布后的临时增删餐或撤回入口，需人工线下协调并在后续版本完善。

饮食标签只是已核实要求与方案之间的人工标记，不是系统营养计算结果。食材、过敏原和标签用相同明确词项进行匹配，不支持医学同义词、交叉过敏、药物或疾病自动推断，不能把“规则匹配”理解为完整安全认证。

## 4. 老人如何选择

老人绑定账号登录后，点击“我的养老 → 我的餐食”。默认展示本周和当天，可切换日期、周次，查看已发布餐食。未发布时明确提示，不展示草稿。

每张卡片列出具体菜品、食材、过敏原、质地、已核实标签、注意事项和剩余份数。匹配条件仅依据人工核对的数据；不满足登记条件时显示具体原因并禁止选餐。资料未知、档案变化、未绑定或已离院时不能确认在院餐食。

选择一套后保存本人记录；同一老人同一天同一餐只有一条当前选择，截止前可改选。客户端不提交老人ID，后端只依据当前登录绑定确定对象。提交带原选餐版本，重复或旧页面提交不产生重复预订。

截止时间按北京时间（Asia/Shanghai）计算，精确到当日设置时间，达到截止时间即拒绝修改。默认早餐06:00、午餐10:00、晚餐16:00，管理员可在发布前调整。过期不能靠修改浏览器时间绕过。

## 5. 变更、库存与厨房汇总

每套方案设置供应上限，后端在事务中锁定周菜单并校验份数，防止并发超订；改选释放原方案占用。已离院记录保留但不占用在院餐食份数。

原档案版本变化后，饮食资料须重新核对；饮食资料重新保存后，原选餐标记待复核。厨房汇总将这些记录单列，不直接计入有效备餐数。老人截止前可以按新要求重新确认；已经截止的异常情况需工作人员人工跟进，当前未提供系统代选或自动替换。

管理员在“厨房汇总”选择已加载菜单中的日期和餐次，查看各方案有效份数、需复核老人及未选餐老人。未选餐名单覆盖所有在院老人，包括尚未绑定账号的老人，便于线下协助。

“已选餐”不代表已配送、已进食或实际摄入；未选餐也不意味着应该不给老人备餐，必须由工作人员跟进。容量限制、核对异常和日期截止不可由Agent放行。

## 6. 数据与权限

| 能力 | 管理员 | 工作人员 | 老人 |
| --- | --- | --- | --- |
| 维护、检查和发布周菜单 | 可 | 不可 | 不可 |
| 查看全院需求及核对 | 可 | 不可（首版） | 不可 |
| 厨房汇总 | 可 | 不可（首版） | 不可 |
| 查看本人已发布菜单、确认选餐 | 不冒充老人 | 不代选（首版） | 绑定本人且满足核对要求时可 |

每周开始日期唯一，必须是周一，完整覆盖21个不重复餐次。草稿保存与发布使用版本校验，发布后不可编辑。老人、日期、餐次组合唯一。需求核对、菜单保存/发布、选餐变更均持久化留痕，不记录账号密码。

## 7. 接口

- 管理员：GET `/api/meals/requirements`；PUT `/api/meals/profiles/{resident_id}`。
- 管理员：GET/PUT `/api/meals/menus`；GET `/api/meals/menus/{id}/coverage`；POST `/api/meals/menus/{id}/publish`。
- 管理员：GET `/api/meals/menus/{id}/kitchen?meal_date=YYYY-MM-DD&meal=lunch`。
- 老人：GET `/api/meals/mine?week_start=YYYY-MM-DD`；PUT `/api/meals/mine` 提交菜单、日期偏移、餐次、方案ID和选餐版本。

老人不能通过请求其他老人ID读取或提交代选；工作人员与老人都不能调用管理员需求和汇总接口。常规私人会话权限不变。

## 8. 验证与试用

后端537项测试、前端79项测试（75项Vitest、4项Node）及TypeScript/Vite构建通过；新增用例覆盖21餐完整性、人工核对、过敏拦截、替代餐覆盖、待核实发布确认、份数与改选、截止、版本、健康变化复核、离院容量、角色越权、跨周复制与参数隔离。

未进行浏览器视觉验收或用户本机数据库实际选餐验证。先用一位虚构老人验证：绑定账号→核对饮食要求→准备未来周菜单→检查覆盖→明确处理其他待核实样例→发布→老人登录选择→管理员查看汇总。不要将100份虚构档案自动批量标记为真实已核实资料。

### 菜单计划流程简化（2026-11-03）

移除管理员页面的“填入参考草稿”入口。以 Agent 生成菜单计划为主要入口，生成结果直接允许管理员逐餐修改；使用“保存修改”保留计划，经全院覆盖检查后发布。仍支持复制上一周计划后调整。页面不再展示“草稿”名称，未发布计划显示为“待发布”。底层未发布状态与版本校验保持不变，生成不会自动发布，老人只能查看已发布菜单。


## 单人档案 AI 辅助读取（2026-11-03）

在“饮食需求”中选择老人后，点击“AI 读取档案并预填”。系统读取当前这位在院老人的过敏记录、饮食记录和健康情况，使用通用模型 `LLM_MODEL`，不使用菜单专用模型。请求不包含姓名、编号、位置和其他老人的资料；档案文本本身请避免填写无关个人信息。

结果只预填当前表单，展示逐条原文依据和待核实问题，不自动保存，不勾选已人工核实。提取字段必须存在可核对的逐字引用，无效引用不采纳；疾病记录不能直接转成禁食或质地要求。原文匹配只能检查引用存在，不能替代医护判断或保证模型正确理解否定语义，请逐条核对。没有明确过敏信息时保持“尚未核实”，没有明确质地时不默认普通质地。

重复读取会提示替换当前未保存表单。读取期间档案版本改变时拒绝应用；切换老人不套用上一个人的结果。预填后补全所需信息、确认核实并点击“保存饮食要求”，才影响覆盖检查、菜单编排和选餐。已有登记在点击保存前不会改变。

验证：相关后端测试16项通过，前端现有81项测试和构建通过。未调用线上模型进行端到端验证。


### 管理入口顺序调整（2026-11-03）

标签顺序为“饮食需求 → 周菜单 → 厨房汇总”，进入餐食管理页默认打开饮食需求，按核实资料、编排发布、汇总备餐的顺序操作。
