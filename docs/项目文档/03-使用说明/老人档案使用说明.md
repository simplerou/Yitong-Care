# 老人档案使用说明

更新日期：2026-11-02。首版功能已写入代码，实际使用前需完成数据库迁移和重启。本环境仅完成 SQLite 接口回归与 MySQL 离线 SQL 检查，尚未完成用户本机 MySQL 迁移或浏览器视觉验收。

[返回文档导航](../README.md) · [实施清单](../01-项目规划/养老院升级实施清单.md)

## 1. 启用

在 `Yitong Care/backend` 目录运行：

```bash
conda activate agent_env
alembic upgrade head
```

迁移 `20261102_0014` 增加 `resident`（档案）、`resident_assignment`（负责关系）、`resident_change`（变更快照）三张表。迁移后重启后端并刷新网页。工具环境连接本机 MySQL 被系统拒绝，本轮没有声称实际建表成功。

## 2. 管理员建档

1. 管理员登录，点击左侧“老人照护 → 老人档案”。
2. 点击“新建档案”，填写姓名和信息来源；其他未知信息可以留空。
3. 补充性别、出生日期、实际入住日期、入住状态、位置和人工照护安排；位置目前为文本登记，不校验床位占用。
4. 填写紧急联系人、过敏、慢病、饮食与吞咽、行动、沟通及其他照护要点。
5. 如需授权工作人员查看，在“负责人员”勾选现有普通账号，核实姓名和掩码手机号后保存。
6. 保存后自动生成稳定档案 ID 和可读档案编号；姓名允许重复，以编号区分不同老人。

出生日期或实际入住日期不得晚于今天，入住不得早于出生。未知过敏等情况不默认填“无”；如已核实没有风险，应人工明确填写并注明来源。照护安排仅是人工登记，不代表系统已作专业评估。

## 3. 查看、查找与更正

列表可按姓名、档案编号、位置和入住状态筛选、分页。工作人员仅看到被分配的老人列表和详情，未授权访问返回 404；只有管理员可以创建、更正和分配，普通账号写接口返回 403。

更正必须填写修改原因；保存时检查档案版本，旧页面遇到其他管理员已保存的新版本会返回 409，并提示重新加载核对，不能静默覆盖。页面离开或重新加载前会提醒未保存修改。

管理员可查看变更记录中的操作者、时间、原因以及前后字段内容。变更快照与档案修改在同一事务中保存，Agent 没有写档案的权限或调用流程。

## 4. 人员分配与权限

多个管理员均可管理单院档案；普通账号只有被管理员显式分配后才能查看对应老人。撤销后后续接口请求即失去该档案权限。该负责关系是首版的逐档案授权，不等于已实现完整员工入职审核、停用、岗位细分或多院权限体系。

公开注册不会自动获得老人资料，负责人员接口仅管理员可用且手机号掩码展示。档案不会写入公共 RAG 或联网查询；私人咨询会话仍保持原有账号隔离。

## 5. 保留与范围

没有物理删除入口；老人离院时把状态改为“已离院”，保留档案与变更。历史测试资料不自动生成真实老人档案，不预填张阿姨、健康分或医嘱。

尚未实现：结构化房间床位和占用冲突、正式任务与测量、异常工单、交接班、Agent 老人上下文、头像/证件附件、档案导出、正式多机构隔离。当前为单院版本，不宣称已全部完成 NH-01～NH-04。

## 6. 接口

所有接口需登录。

| 接口 | 权限 | 用途 |
| --- | --- | --- |
| GET /api/residents | 管理员 / 已分配人员 | 分页查询授权档案摘要 |
| GET /api/residents/{id} | 管理员 / 已分配人员 | 档案详情 |
| POST /api/residents | 管理员 | 创建档案 |
| PUT /api/residents/{id} | 管理员 | 完整更新，需 version 和 change_reason |
| GET /api/residents/assignees | 管理员 | 现有普通账号候选，姓名和掩码手机号 |
| GET /api/residents/{id}/changes | 管理员 | 分页变更快照 |

## 7. 验证与人工试用

后端 522 项测试、前端 69 项测试（65 项 Vitest、4 项 Node）及 TypeScript/Vite 构建通过。新增用例覆盖建档、读取、更正、筛选、离院保留、变更快照、乐观版本冲突、普通账号不能写入、跨账号访问与撤权、字段校验、多管理员管理。

建议迁移后用虚构资料手工验证：管理员新建一份→分配工作人员 A→A 只读查看→未分配人员 B 无记录→管理员将 A 改为 B→A 刷新后失去访问、B 可查看→两个管理员同时编辑并核对冲突提示。切勿用真实老人隐私充当公开测试资料。

## 8. 导入100份虚构测试档案

已准备 `backend/fixtures/residents_demo_100.json`，为固定版本的虚构数据：100人、90位在院和10位离院，年龄按2026-11-02基准为60～99岁，覆盖未评估、自理、部分协助、全面协助和专人照护。姓名使用普通姓名，不带“测试·”前缀，楼栋使用 A/B/C/D；来源及照护备注明确标注虚构；联系电话全部留空，不能据此执行真实照护。

在 `backend` 目录、激活 `agent_env` 后执行：

```bash
alembic upgrade head
python -m scripts.seed_residents
```

只有一个管理员时自动将其记为导入操作人；多个管理员时使用 `python -m scripts.seed_residents --admin-phone 管理员手机号` 明确指定，不创建或提权任何账号。导入后管理员刷新老人档案列表即可查看，需向工作人员开放时再逐人分配。

脚本使用固定ID和 `DEMO202611-001`～`DEMO202611-100` 编号，重复执行跳过已有样例，不覆盖人工修改。导入及100条创建审计在同一事务中完成，中途失败整体回滚；不删除已有正式档案，不自动授权工作人员，不调用模型或Embedding。可用 `python -m scripts.seed_residents --validate-only` 离线校验，不连接数据库。

新增导入测试验证100条样例唯一、90个在院登记位置不重复、审计完整、无自动分配、重复导入不覆盖人工修改、途中失败全部回滚。两项测试通过。当前工具环境实际MySQL导入失败，以上说明不代表本机已有100条档案；需执行上述命令完成实际写入。

### 调整已导入批次的显示

姓名已移除“测试·”，楼栋更新为 A楼、B楼、C楼、D楼。若已导入旧数据，在 backend 目录执行：

```bash
python -m scripts.seed_residents --refresh-labels
```

只处理本批次固定 ID/编号，去掉旧姓名前缀，并将仍为原始“演示楼”格式的位置改为 A/B/C/D；保留人工改过的位置、其他档案内容和负责关系，写入版本及变更记录。再次执行不重复修改。来源和备注继续保留虚构资料标识；离院样例仍无在院位置。多个管理员时追加 `--admin-phone 管理员手机号`。

该显示调整的3项导入回归测试通过；本机数据库连接仍受工具环境限制，需用户终端执行命令实际更新。
