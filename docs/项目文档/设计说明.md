## 一、设计思路：先拆解浙里办，再做养老场景的加减法

浙里办给用户的感受不是"功能多"，而是**入口清楚、卡片直白、操作有回音**。我把它的设计经验拆成 5 条，落到本项目：

| 浙里办的做法 | 在本项目中的落地 |
| --- | --- |
| 统一门户、统一头部 | 顶栏固定：品牌 + 全局知识搜索 + 长辈模式 + 消息 + 用户身份 |
| 服务卡片化、白话命名 | 首页「智能体服务」6 张卡片，一卡一个业务定位，配一句人话说明 |
| 层级浅、入口稳定 | 左侧菜单常驻，6 个 Agent、5 个 RAG 环节各自独立入口，不藏在二级 tab 里 |
| 状态可见、结果可查 | 文档状态、进度条、命中数量、参考来源、检索记录全程留痕 |
| 适老化 | 独立「长辈模式」：字号、行高、按钮点击区整体放大 |

养老场景额外补 3 件事：

1. **答案必须能核对**：智能体的每条回答带 `【1】【2】` 角标，右侧联动原文片段，弹窗显示来源、字符区间、段落序号。
2. **RAG 不是黑盒**：把「上传 → 切块 → 入库 → 检索 → 原文」做成首页 1–5 步流水线，每一步都有独立菜单和数量统计，评审可以直接按顺序走一遍。
3. **医疗/政策场景要克制**：回答带免责声明，用药类问题先给出"请勿自行调整"的安全提示，并提供「转人工」出口。

## 二、信息架构与菜单地图

```
颐养通
├─ 顶栏：品牌 / 全局知识搜索 / 长辈模式 / 消息 / 用户
├─ 工作台
│   └─ 首页工作台
├─ 智能体服务（每个 Agent 一个独立菜单）
│   ├─ 健康管家      健康监测与慢病咨询
│   ├─ 用药管家      用药提醒与配伍风险
│   ├─ 政策顾问      养老补贴与政策解读
│   ├─ 膳食营养师    慢病食谱与营养搭配
│   ├─ 安全守护      跌倒预防与应急处置
│   └─ 心灵陪伴      情绪疏导与社交连接
├─ 知识库与 RAG（链路的每一步都是独立菜单）
│   ├─ 知识库管理    文档上传 / 解析 / 删除
│   ├─ 文本切块      切块参数 / 实时预览 / 保存
│   ├─ 向量入库      Embedding / 批次 / 进度
│   ├─ 向量检索      查询 / 范围 / TopK / 阈值 / 结果
│   └─ 检索记录      历史查询 / 回看 / 删除
└─ 运营管理
    └─ 服务记录      问答留痕 / 引用数量 / 跳转对话
```

设计取舍：

- **为什么用"顶栏 + 左侧常驻菜单"，而不是纯顶部导航？**
  验收要求"每个智能体单独对应一个菜单入口"。顶部下拉菜单需要一次 hover 才能看到全部 Agent，左侧常驻则一眼可见、可直接点击、可高亮当前项，也更适合后台型平台。
- **为什么 RAG 要拆成 5 个菜单，而不是一个"知识库"页？**
  需求明确要求"切块、检索拥有独立菜单操作入口"。拆开之后，每一步都能单独演示、单独验收，也方便后续做权限（例如只有管理员能重建向量）。
- **为什么首页仍然保留"服务大厅"式卡片？**
  浙里办的熟悉感来自首页，而不是后台表格。首页承担"找服务"和"看状态"两件事，进入具体页面后再切换到工作台布局。

## 三、视觉规范

### 3.1 色彩

| 角色 | 色值 | 用途 |
| --- | --- | --- |
| 政务蓝（主色） | `#1B64F2` | 主按钮、选中态、关键数字 |
| 深蓝 | `#0B3E9E` → `#2472FF` | 顶栏渐变、首页 Hero |
| 页面底色 | `#F3F6FC` | 内容区背景 |
| 卡片 / 描边 | `#FFFFFF` / `#E4EAF4` | 卡片、表格分隔 |
| 正文 / 次要 | `#152238` / `#6B7C95` | 标题、说明文字 |
| 成功 / 警示 / 危险 | `#0FA968` / `#E8930C` / `#E5484D` | 状态标签、进度、删除 |

6 个智能体各有辅色（健康蓝、用药绿、政策紫、膳食橙、安全红、心理粉），**只用于图标底色、标签和强调线**，不大面积铺色，保证整体仍是一个统一的政务产品。

### 3.2 字号与圆角

- 基础字号 14px，正文 13.5–14px，说明文字 11.5–12.5px，页面标题 24px。
- 卡片圆角 16px，按钮/输入框 10–12px，标签 6–8px。
- 阴影极轻（`0 2px 8px rgba(18,42,82,.05)`），靠描边和留白分层，避免"互联网感"过重。

### 3.3 适老化（长辈模式）

右上角一键切换，`html.senior` 下统一放大：

- 基础字号 14 → 16px，聊天正文 13.5 → 16px，行高 1.78 → 1.85；
- 菜单项 42 → 48px，按钮 38 → 44px，表格字号 +1.5px；
- 首页标题 30 → 34px，并保留所有文字标签（不用纯图标表达关键操作）。

## 四、页面设计说明

### 4.1 首页工作台

![首页](../web示例/screenshots/01-home.png)

- **Hero 区**：问候 + 日期 + 待办数量 + 两个主行动（开始咨询 / 长辈模式）；右侧健康分环与今日守护清单，把"服务"和"状态"放在同一屏。
- **数据条**：知识文档 / 文本块 / 向量条目 / 今日问答，四个数字直接反映知识库规模，点菜单时数值同步变化。
- **智能体服务**：6 张卡片，每张包含业务定位、一句话说明、"已接入 N 个知识库"标签，整卡可点。
- **RAG 全链路**：5 个步骤卡（文档上传 → 文本切块 → 向量入库 → 向量检索 → 结果与原文），带序号、连接箭头和实时数量，既是说明也是入口。
- **今日守护 / 最近对话**：待办可勾选并即时反馈；最近对话可回到对应 Agent。

### 4.2 智能体对话页（6 个 Agent 共用一套模板，配置驱动）

![智能体对话](../web示例/screenshots/02-agent.png)

- 顶部身份条：图标、名称、在线状态、业务定位、已接入知识库、清空对话 / 转人工。
- 左对话区：欢迎语 + 3 个推荐问题；发送后依次出现「正在检索知识库」→「已命中 N 条资料 · 正在生成」→ 流式回答。
- 回答内 `【1】【2】` 角标可点击，打开对应原文弹窗。
- 右侧「参考知识」：显示最近一次检索命中的片段、相关度、文档名、段号、字数；点击同样打开原文。
- 回答底部固定一条「答案引用了 N 条知识库原文，点击编号可核对出处」，把 RAG 证据链显性化。
- 回答下方提供「有帮助 / 需改进 / 重新生成」，为后续质量运营留接口。

### 4.3 知识库管理

![知识库管理](../web示例/screenshots/03-kb.png)

- 拖拽上传区 + 选择文件 + 载入示例文档（方便评审快速走通流程）。
- 文档表格：名称 / 类型 / 大小 / 已切块 / 状态 / 上传时间 / 操作（查看、切块、入库、删除）。
- 状态机：`解析中 → 待处理 → 已切块 → 已入库`，不同状态用不同颜色标签。
- 删除走二次确认弹窗，明确告知会同时删除文本块与向量。

### 4.4 文本切块

![文本切块](../web示例/screenshots/04-chunk.png)

- 左侧参数卡：文档选择、切块大小（100–500 字）、重叠长度（0–100 字）、三档预设、策略说明。
- 右侧实时预览：拖动滑块立即重算"预计 N 段 / 平均 N 字"，每段显示字数与重叠字数，点击可看全文。
- **只有点击「保存切块结果」才写入知识库**，保存后提示"请重新执行向量入库"，避免旧向量残留。
- 切分策略：按句号、问号、分号、换行优先切分；超长句按字符硬切；重叠区按整句回退，避免新片段从半个句子开始。

### 4.5 向量入库

![向量入库](../web示例/screenshots/05-vector.png)

- 选择文档、Embedding 模型、批次大小；展示"当前文档已入库 x / y 段"。
- 右侧进度：百分比大数字、进度条、三步状态（读取文本块 → 生成向量 → 写入索引）、深色运行日志（逐批输出）。
- 下方索引概览：向量总数、维度、索引类型（FAISS FlatIP / 余弦）、索引版本、覆盖文档数。
- 重新切块会使该文档向量失效，页面会提示需要重新入库。

### 4.6 向量检索

![向量检索](../web示例/screenshots/06-search.png)

- 顶部查询框 + 知识范围 + TopK + 语义余弦下限；底部给出 4 个示例问题。
- 结果卡片：排名、文档名、段号、类型、命中片段（关键词高亮）、来源、字符区间、字数、综合得分/余弦值、相关度百分比与进度条。
- 顶部汇总：命中数量、检索耗时、索引规模、TopK 与阈值，便于演示"检索确实发生了"。
- 「查看原文」直接打开原文弹窗，可上一段/下一段、复制原文。

### 4.7 原文片段弹窗

![原文片段](../web示例/screenshots/07-original.png)

- 元信息：文件类型、来源机构、字符区间、字数、是否已向量化。
- 全文展示，命中关键词高亮；底部「上一段 / 下一段 / 复制原文 / 关闭」。
- 弹窗层级高于页面，Esc 或点击遮罩可关闭，符合"检索结果可查看原文片段"的验收要求。

### 4.8 检索记录 / 服务记录

- **检索记录**：查询内容、时间、命中数量、Top1 得分、Top1 来源；支持"查看结果"还原当时的结果列表，也支持删除/清空。
- **服务记录**：每次问答的时间、智能体、居民问题、引用资料数、状态；可跳回对应 Agent 继续对话。为后续服务质量评估、工单流转预留字段。

## 五、RAG 全链路交互设计（重点）

```
上传文档 ──► 解析正文 ──► 文本切块 ──► 向量化 ──► 写入向量索引
   │             │             │            │
   └─ 文档表     └─ 状态标签   └─ 预览/保存  └─ 进度/日志
                                             │
用户提问 ──► 查询改写(预留) ──► 语义余弦过滤 + BM25 召回 ──► RRF 融合取 TopK ──► 拼上下文
                                             │
                          流式回答 + 引用角标 ◄┘
                                   │
                          点击角标 ──► 原文弹窗（来源/段号/字符区间）
```

**每一步的反馈设计：**

| 环节 | 操作反馈 |
| --- | --- |
| 上传 | 拖拽高亮、解析中标签、完成 toast、文档数即时 +1 |
| 切块 | 滑块实时改数字、预览即时刷新、保存后提示段数并引导下一步 |
| 入库 | 进度条 + 百分比 + 批次日志 + 三步状态，完成后集合统计更新 |
| 检索 | 加载态、命中汇总、结果卡片、空结果提示（建议降低阈值/扩大范围） |
| 原文 | 弹窗、关键词高亮、字符区间、复制、上一段/下一段 |
| 问答 | 检索中 → 命中 N 条 → 流式生成 → 引用角标 → 右侧证据 → 反馈按钮 |

> 原型里的切块、向量化、余弦检索是**浏览器端真实计算**（哈希 n-gram 向量 + IDF 词面加权混合召回），所以任意问题都会得到真实排序结果。生产环境只需把 `chunkText / embed / retrieve` 三个函数替换为后端接口，交互与页面不用改。

## 六、工程化落地方案

原型用原生 HTML/CSS/JS，目的是**零依赖、双击即看、方便评审**。正式开发建议：

> 代码工程根为 `Yitong Care/`（独立 Git 仓库，目录名含空格，命令中需加引号）：前端在 `Yitong Care/frontend/`，后端在 `Yitong Care/backend/`，部署在 `Yitong Care/deploy/`；`项目文档/` 与 `web示例/` 留在项目总目录，不进入代码仓库。

### 6.1 前端

- Vue 3 + Vite + TypeScript
- Vue Router（路由即菜单，`meta.title / meta.icon / meta.group` 驱动侧边栏）
- Pinia（知识库、会话、检索状态）
- Element Plus（表格、弹窗、上传、进度条）+ 自定义主题变量覆盖为政务蓝
- ECharts（后续服务统计）
- `markdown-it` + `DOMPurify` 渲染回答，SSE 流式输出
- 目录建议：

```
src/
├─ layouts/AppLayout.vue          # 顶栏 + 侧边栏 + 内容区
├─ router/index.ts                # 路由与菜单同源
├─ views/
│  ├─ Home.vue
│  ├─ agent/AgentChat.vue         # 6 个 Agent 共用
│  ├─ kb/DocumentList.vue
│  ├─ kb/ChunkPreview.vue
│  ├─ kb/Vectorize.vue
│  ├─ kb/Retrieval.vue
│  ├─ kb/RetrievalLogs.vue
│  └─ ops/ServiceRecords.vue
├─ components/  SourceDrawer / CitationChip / UploadDropzone / StatusTag
├─ stores/      agent.ts / knowledge.ts / retrieval.ts
└─ api/         http.ts / sse.ts
```

### 6.2 后端与 RAG

- FastAPI（Python 3.11，已确认）：异步、OpenAPI、RAG 生态均合适
- 文档解析：`pypdf` / `python-docx` / `unstructured`
- 切块：`RecursiveCharacterTextSplitter`，separators 设为 `["\n\n", "\n", "。", "！", "？", "；", ""]`，带 overlap
- Embedding：`bge-m3` / `bge-large-zh-v1.5`，或通义 `text-embedding-v3`（DashScope）
- 数据库：**MySQL 8.0**（utf8mb4 / InnoDB），业务数据、文本块与 embedding 的唯一数据源
- 向量索引：**FAISS**（faiss-cpu），`IndexIDMap2(IndexFlatIP)` + 向量归一化；索引文件版本化落盘
- 索引管理：自研 `IndexManager`，单写者 + 版本号 + 临时文件原子替换 + 读侧热加载；`rebuild_index.py` 支持对账重建
- 召回：FAISS 语义召回 + BM25（jieba 分词、Okapi）关键词召回，RRF 排名融合；`bge-reranker` 重排（P1）
- 生成：**通义千问**（Qwen，DashScope，SSE 流式）；Prompt 中要求"只依据给定片段回答，并标注 [1][2]"
- 引用：后端返回 `citations: [{index, chunk_id, doc_id, doc_name, page, start, end, score}]`，前端只负责渲染和定位
- 存储：MySQL 8.0（文档/会话/日志/embedding）、MinIO（原文件）、Redis（会话与限流）

#### 6.2.1 存储与索引设计：MySQL + FAISS

**为什么这样选：**

- **规模匹配**：试点 20–100 份文档、约 1–5 千个文本块；1024 维 Flat 索引常驻内存约 4–20MB，检索毫秒级。
- **运维最简**：不引入 Milvus/Qdrant 等独立向量库，少一个需要部署、备份、监控、升级的组件。
- **数据主权**：MySQL 保存 chunk 正文与 embedding BLOB（float32，约 4KB/段），FAISS 仅作派生索引；索引损坏或模型升级时可全量重建。
- **权限过滤**：按知识库分索引（`kb_id`），检索时只查授权索引，避免跨库召回被稀释。
- **可演进**：`VectorStore` 接口隔离 `add / remove / search / rebuild / health`；向量超过 20 万、需要多实例或复杂过滤时，可平滑切换 Milvus/Qdrant。

**需要接受的约束：**

1. FAISS 不是数据库：不提供持久化、事务、权限、过滤，均由 MySQL 与应用层补足。
2. 多进程一致性：写入由 Worker 执行，API 只读；同一索引同一时刻只允许一个写者。索引加载在进程内存中，API 按 `vector_index.version` 热加载；试点期建议 API 单 worker，或独立向量服务。
3. 删除与更新：Flat + `IndexIDMap2` 支持 `remove_ids`；重建期间读旧版本、写新版本，完成后原子切换。
4. 容量上限：Flat 为精确检索，建议 ≤ 20 万向量；超过后改用 HNSW/IVF 或迁移独立向量库。

**索引生命周期：**

```
切块保存 ──► 写入 MySQL（chunk + embedding）──► 标记待入索引
                                                    │
                                                    ▼
                                        IndexManager.add_with_ids
                                                    │
                                     写临时文件 → fsync → 原子 rename
                                                    │
                                     更新 MySQL vector_index 版本号
                                                    │
                                     读侧按版本号热加载（或单进程直接切换）
```

**重建与对账：** 启动时比对 `vector_index.vector_count` 与 MySQL 已向量化条数；不一致、模型维度变化或索引损坏时执行全量重建。索引文件可丢失，MySQL 中的 embedding 保证可恢复。

### 6.3 核心接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/documents` | 上传文档（multipart），返回解析任务 |
| GET | `/api/documents` | 文档列表（状态、切块数、向量数） |
| DELETE | `/api/documents/{id}` | 删除文档及块/向量 |
| POST | `/api/documents/{id}/chunks:preview` | 按 size/overlap 预览切块 |
| POST | `/api/documents/{id}/chunks` | 保存切块 |

## 九、原型边界（需要提前说明）

1. 原型没有真实后端，数据保存在浏览器内存，**刷新后恢复示例数据**（长辈模式偏好除外）。
2. PDF / Word 无法在前端真正解析，原型使用内置样例正文；TXT / Markdown 会读取真实内容。
3. 向量化使用前端哈希 n-gram（384 维）模拟 Embedding，检索为"余弦相似度 + IDF 词面加权"的混合召回，**用于验证交互与链路，不代表生产检索效果**。生产环境由 MySQL 8.0 + FAISS 实现，MySQL 为唯一数据源，FAISS 索引可重建。
4. 回答由模板 + 检索片段拼装，不是真实大模型生成；生产接入 LLM 后，页面与交互无需改动。
5. 「转人工」「消息通知」为演示交互，不会真实外呼或发消息。

### 检索实现更新（2026-10-28）

当前后端采用 Embedding + FAISS 语义召回、jieba 分词的 BM25 Okapi 关键词召回和 RRF 排名融合。MySQL 是文档、切块、向量及历史记录的唯一数据源；原有 FULLTEXT 索引保留，但当前召回不使用它。原型中的哈希/IDF 演示说明只对应冻结的浏览器原型。

两路均先限制知识范围、已完成文档、模型和维度；BM25 使用范围内全部合格切块统计词频，k1=1.5、b=0.75、IDF=ln(1+(N-df+0.5)/(df+0.5))，同一查询词计一次。每路最多 60 条，全局语义候选在各知识库召回后合并排序。RRF=Σ1/(60+rank)，排名从 1 开始，未召回贡献 0，按融合得分降序、块 ID 升序取 TopK。

API `threshold` 保留字段名与 0.02–0.6 范围（默认 0.12），新策略含义为语义余弦下限；BM25 不受该阈值过滤。`strategy=bm25_rrf`，`score` 为原始 RRF 分数，`bm25_score` 为原始 BM25 分数，另返回 `semantic_rank`、`bm25_rank`。两路命中时 RRF 理论最高为 2/61≈0.032787，不能当作概率或百分比。`lexical_score` 在新策略中等于原始 BM25 分数，保留供兼容。旧记录标记 `legacy_weighted`，保持原有分数与阈值含义，不重新计算。

更新需执行 `cd "Yitong Care/backend"` 后运行 `python -m alembic upgrade head`（迁移 0004）。无需重新向量化或重建 FAISS。当前 BM25 每次请求读取范围内切块并构建词频统计，尚无缓存/独立搜索服务，大规模使用前应压测并评估持久倒排索引；Rerank、查询改写及业务评测集仍待实现，不能据融合方式直接宣称效果提升。
