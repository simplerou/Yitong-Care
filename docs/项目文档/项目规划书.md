## 1. 编制说明

### 1.1 目的

本规划书用于指导「颐养通」从可点击原型进入工程化建设，回答四个问题：

1. **建什么**：本期范围、边界与交付物；
2. **怎么建**：技术路线、架构与项目目录结构；
3. **谁来建**：角色分工与协作机制；
4. **何时算完成**：里程碑、验收标准与试点指标。

### 1.2 与需求文档的关系

- 需求文档定义"做什么、做到什么程度"；本规划书定义"怎么排、谁来做、放在哪"。
- 本规划书中的任务编号与需求编号（FR-*）、验收编号（AC-*）一一对应，见第 7.2 节与第 13 章。
- 需求变更时，先更新需求文档基线，再同步调整本规划书的 WBS 与里程碑。

## 2. 项目概述

### 2.1 建设背景

社区居家养老场景中，健康、用药、政策、膳食、安全、心理六类知识分散，老年人获取困难，社区顾问重复答疑。项目通过「6 个业务智能体 + 统一知识库 + RAG 全链路」构建服务门户，让答案有出处、服务可运营、过程可追溯。

### 2.2 建设目标

| 编号 | 目标 | 验收关联 |
| --- | --- | --- |
| G1 | 统一门户，菜单不超过两级 | AC-02、AC-06 |
| G2 | 6 个智能体，各有独立定位与知识范围 | AC-01、AC-05 |
| G3 | RAG 五步链路可由社区人员独立操作 | AC-03、AC-04 |
| G4 | 回答带引用，可查看原文与字符位置 | AC-05、AC-07 |
| G5 | 长辈模式与基础无障碍 | AC-06、可用性测试 |

### 2.3 建设原则

1. **原型先行**：以已评审的 `web示例/` 作为视觉与交互基线，正式前端按组件化重写，不直接改原型。
2. **前后端分离**：前端只负责展示与交互，检索、生成、引用全部由后端返回。
3. **RAG 可替换**：解析、切块、Embedding、向量索引、重排均以接口/适配器隔离，便于替换模型与供应商。
4. **智能体配置化**：新增业务智能体只新增配置与知识库，不复制页面与接口。
5. **证据优先**：任何回答必须携带 citations；无命中时明确兜底，不编造。
6. **安全合规**：健康与个人信息最小化采集、脱敏展示、权限隔离、全程留痕。

┌───────────────▼──────────────────────────────────────────────┐

│  ├─ 文档 / 切块 / 向量任务 / 检索 / 会话 API                   │

              ┌──────▼──────┐        ┌────────────────┐

### 5.2 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 前端框架 | Vue 3 + Vite + TypeScript | 团队上手快，生态成熟，适配政务项目交付 |
| UI | Element Plus + 自定义主题 | 表格/上传/弹窗/进度组件齐全，覆盖后台场景 |
| 状态与路由 | Pinia + Vue Router | 路由即菜单，便于权限与面包屑 |
| 流式问答 | SSE（fetch + ReadableStream） | 比 WebSocket 简单，穿透代理稳定 |
| 后端 | FastAPI（Python 3.11，已确认） | 异步、OpenAPI 与 RAG 生态合适 |
| 数据库 | MySQL 8.0（utf8mb4 / InnoDB） | 团队熟悉、运维简单；存业务数据、chunk 正文与 embedding BLOB |
| 向量索引 | FAISS（faiss-cpu，FlatIP + IDMap2） | 单机精确检索、零额外服务；索引文件可重建 |
| 词面检索 | BM25 Okapi（jieba） + RRF | 中文关键词召回，与 FAISS 语义召回融合 |
| 索引管理 | 自研 IndexManager + rebuild_index.py | 版本化、原子替换、对账重建、读侧热加载 |
| 缓存/队列 | Redis + ARQ/Celery | 解析与向量化异步化 |
| 对象存储 | MinIO | 私有化部署，兼容 S3 |
| 文档解析 | pypdf / python-docx / Unstructured + OCR | 覆盖 PDF/Word/扫描件 |
| Embedding | bge-m3 / bge-large-zh-v1.5，或通义 text-embedding-v3 | 中文效果好，可私有化或走 DashScope |
| 重排 | bge-reranker（P1） | 提升 TopK 准确率 |
| 大模型 | 通义千问（Qwen，DashScope） | 已确认；中文效果好，支持 SSE 流式 |
| 部署 | Docker Compose + Nginx | 无需独立向量库，后续可上 K8s |

### 5.3 环境规划

| 环境 | 用途 | 配置建议 | 数据 |
| --- | --- | --- | --- |
| 开发（dev） | 本地开发与联调 | 开发机 Docker Compose：MySQL/Redis/MinIO + 本地 FAISS 索引目录 | 示例数据 |
| 测试（test） | 集成测试、UAT | 1 台 8C16G，500GB 磁盘 | 脱敏测试数据 |
| 试点（prod） | 社区试点 | 应用 2 台 8C16G（建议 32G 内存，FAISS 常驻）；MySQL 云 RDS；对象存储 500GB | 真实授权数据 |
| 模型服务 | LLM / Embedding | 公有云 API 或 GPU 服务器（按选型） | — |

### 5.4 关键技术决策

| 决策 | 方案 | 影响 |
| --- | --- | --- |
| 数据主权 | MySQL 为唯一数据源，embedding 存 BLOB，FAISS 仅作派生索引 | 索引损坏或模型升级可全量重建 |
| 索引一致性 | 单写者 + 版本号 + 临时文件原子替换 + 读侧热加载 | 多 worker 不会读到写了一半的索引 |
| 检索策略 | FAISS 向量召回 + BM25 关键词召回 + RRF 排名融合，P1 增加 Rerank | 兼顾语义与政策编号等精确匹配 |
| 规模边界 | FlatIP 建议 ≤ 20 万向量，超出迁 HNSW 或独立向量库 | 预留平滑演进路径 |
| 引用生成 | 后端返回 citations，前端只渲染 | 避免前端猜测出处，保证可追溯 |
| 长任务 | 上传解析、向量化走异步任务，前端轮询/SSE | 避免请求超时，支持进度与重试 |
| 智能体 | YAML 配置 + 注册表 + 统一 Prompt 模板 | 新增业务不改代码 |
| 权限 | JWT + RBAC，菜单与接口双重校验 | 满足社区多角色 |
| 降级 | LLM 超时返回检索片段 + 重试入口 | 保证可用性 |

## 6. 项目目录结构与代码总体架构

### 6.1 目录设计原则

1. **顶层只有三个文件夹**：`项目文档/`、`web示例/`、`Yitong Care/`；不把 README、Makefile、CI 等工程配置散落在根级（Git 元数据除外）。
2. **代码独立仓库**：`Yitong Care/` 是独立 Git 仓库，代码、CI、构建、部署、测试、脚本全部内聚其中，可在 IDE 中单独打开。
3. **文档与代码分离**：`项目文档/` 存放需求、设计、规划、测试与验收材料；`web示例/` 作为已评审原型冻结保留；两者不进入代码仓库，避免被构建或镜像打包。
4. **业务分层**：后端按 `api → services → models/schemas` 分层，RAG 能力以 `services/` 下的子域隔离。
5. **配置外置**：智能体、Prompt、环境变量、模型参数均不入业务代码。
6. **测试同仓**：单元测试贴近代码，跨端 E2E 放 `Yitong Care/tests/e2e/`。
7. **可部署**：`Yitong Care/deploy/` 提供一键启动与生产配置，运行目录与代码目录分离。

### 6.2 仓库总体结构

> 项目总目录只保留三个文件夹：`项目文档/`、`web示例/`、`Yitong Care/`。`Yitong Care/` 是**独立 Git 仓库**，工程代码、CI、构建、部署、测试全部放在其中；项目总目录不再放根级 README、Makefile、`.github` 等文件。

**总目录（文档 / 原型 / 代码仓库）：**

```
颐养通-智能养老服务平台/
├─ 项目文档/                         # 需求、设计、规划、测试、验收
├─ web示例/                          # 已交付原型（冻结，不参与构建）
└─ Yitong Care/                      # ★ 独立 Git 仓库（代码工程根）
```

**Yitong Care（代码仓库）内部：**

```
Yitong Care/
├─ .git                              # 独立仓库（submodule 时是 gitfile）
├─ .github/
│  └─ workflows/
│     ├─ ci-frontend.yml             # 前端 lint + unit + build
│     ├─ ci-backend.yml              # 后端 lint + pytest
│     └─ deploy.yml                  # 测试/试点环境部署（手动触发）
├─ README.md                         # 代码仓库说明、启动方式、目录导航
├─ Makefile                          # dev / test / build / deploy
├─ .gitignore
├─ .editorconfig
├─ frontend/                         # Vue 3 前端
├─ backend/                          # FastAPI + RAG 服务
├─ deploy/                           # Docker Compose、Nginx、初始化脚本
├─ scripts/                          # 开发/运维辅助脚本
└─ tests/
   └─ e2e/                           # Playwright 跨端端到端用例
```

**Git 管理方式（二选一）：**

| 方式 | 做法 | 适用 |
| --- | --- | --- |
| 推荐：submodule | 总仓库用 `git submodule add` 引入 `Yitong Care`；总仓库只跟踪文档、原型与子模块指针，代码仓库独立提交 | 希望一个总目录 clone 全部内容 |
| 工作区 | 总目录不初始化 Git，只把 `Yitong Care/` 作为代码仓库 | 文档与原型不需要版本管理 |

> 使用 submodule 时，根目录会多出 `.gitmodules`（Git 元数据，不属于工程文件）；若希望顶层严格只有三个文件夹，可不初始化外层 Git，直接把总目录当作工作区。
>
> 不要在外层总仓库直接 `git add "Yitong Care"`：Git 会把它记成 gitlink，克隆后目录为空。必须用 submodule，或在外层忽略该目录。
>
> 当前 `Yitong Care/` 仍为空目录，待执行 `git init` 并建立首个提交。进入代码仓库后命令均在 `Yitong Care/` 下执行，例如 `cd "Yitong Care" && make dev`；目录名含空格，命令中需要加引号。

### 6.7 扩展约定

**新增一个智能体（目标 ≤ 0.5 人天）**

1. 在 `Yitong Care/backend/app/agents/configs/` 新增 `{id}.yaml`：名称、定位、图标、主题色、`kb_ids`、推荐问题、Prompt。
2. 在 `Yitong Care/backend/app/prompts/` 按需新增提示词片段。
3. 在 `Yitong Care/frontend/src/config/agents.ts` 增加菜单项（若菜单由接口下发则跳过）。
4. 绑定知识库并完成切块/入库。
5. 在 `Yitong Care/tests/e2e/` 增加一条 `agent-{id}.spec.ts`，更新需求文档的知识范围表。

**新增一个页面**

1. `Yitong Care/frontend/src/views/{domain}/XxxView.vue` + 路由 + 菜单权限标识。
2. 接口放 `Yitong Care/frontend/src/api/`，类型放 `Yitong Care/frontend/src/types/`。
3. 状态放对应 store；通用交互复用 `components/common/`。

**新增一个 RAG 能力**

1. 在 `Yitong Care/backend/app/services/` 对应子域实现，先定义 `base.py` 接口。
2. 通过配置切换实现（如 `FAISS_INDEX_DIR`、`FAISS_INDEX_TYPE=flat`），模型或维度变化时触发重建。
3. 补单元测试与评测集回归。

### 检索实现更新（2026-10-28）

当前后端采用 Embedding + FAISS 语义召回、jieba 分词的 BM25 Okapi 关键词召回和 RRF 排名融合。MySQL 是文档、切块、向量及历史记录的唯一数据源；原有 FULLTEXT 索引保留，但当前召回不使用它。原型中的哈希/IDF 演示说明只对应冻结的浏览器原型。

两路均先限制知识范围、已完成文档、模型和维度；BM25 使用范围内全部合格切块统计词频，k1=1.5、b=0.75、IDF=ln(1+(N-df+0.5)/(df+0.5))，同一查询词计一次。每路最多 60 条，全局语义候选在各知识库召回后合并排序。RRF=Σ1/(60+rank)，排名从 1 开始，未召回贡献 0，按融合得分降序、块 ID 升序取 TopK。

API `threshold` 保留字段名与 0.02–0.6 范围（默认 0.12），新策略含义为语义余弦下限；BM25 不受该阈值过滤。`strategy=bm25_rrf`，`score` 为原始 RRF 分数，`bm25_score` 为原始 BM25 分数，另返回 `semantic_rank`、`bm25_rank`。两路命中时 RRF 理论最高为 2/61≈0.032787，不能当作概率或百分比。`lexical_score` 在新策略中等于原始 BM25 分数，保留供兼容。旧记录标记 `legacy_weighted`，保持原有分数与阈值含义，不重新计算。

更新需执行 `cd "Yitong Care/backend"` 后运行 `python -m alembic upgrade head`（迁移 0004）。无需重新向量化或重建 FAISS。当前 BM25 每次请求读取范围内切块并构建词频统计，尚无缓存/独立搜索服务，大规模使用前应压测并评估持久倒排索引；Rerank、查询改写及业务评测集仍待实现，不能据融合方式直接宣称效果提升。
