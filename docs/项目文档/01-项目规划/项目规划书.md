## 1. 建设目标

在现有六个 Agent、账号权限、私人会话及 RAG 链路上，增加养老院日常照护业务。先跑通“老人档案—照护任务—异常跟进—交接确认”，再让 Agent 接入老人授权上下文和业务草稿。

本期单院、两类角色：管理员和工作人员。管理员为一种权限角色，可有多个独立账号，不做单例管理员，也不继续细分院长、系统管理员、护理主管。开发人员的项目分工不等于产品账号角色。

## 2. 可复用基础与待建设项

| 可复用基础 | 使用要求 |
| --- | --- |
| Vue 3、TypeScript、Pinia、现有布局与组件 | 新业务页沿用品牌与无障碍规范，不将旧原型当作养老院成品 |
| FastAPI、SQLAlchemy、Alembic、MySQL | 新增业务实体、迁移、服务层鉴权和审计 |
| 账号、管理员角色、会话所有权 | 复用身份，新增员工准入和老人负责关系 |
| LangGraph、Qwen、领域规则与证据检查 | 保留安全分支，增加老人上下文和草稿人工确认 |
| Embedding、FAISS、BM25、RRF、Tavily | 保留检索链路，补本院知识版本与审核；联网不发送老人隐私 |
| 本地今日提醒、现有最近对话 | 最近对话继续使用；本地提醒不能作为正式任务数据库 |

老人档案、床位、正式任务、测量记录、异常业务流、交接班和机构统计均属新增规划。六个 Agent 有基础代码不代表机构场景已联调验收。

| 阶段 | 交付物 | 需求关联 | 进入下一阶段的条件 |

| M1 人员与老人基础 | 员工开通、空间床位、老人档案、人员分配、基础审计 | NH-01～04、14 | 两名工作人员的负责范围与访问边界验收通过 |
| M2 照护执行 | 数据库任务、执行记录、测量记录、异常上报及复核 | NH-05～08、14 | 完成一次“任务→记录→异常处理”闭环 |
| M3 交接班 | 交接草稿、提交、接收、未处理事项追踪 | NH-09 | 交班与接班由不同账号完成，有时间与状态记录 |

M1 是后续数据前提；M2 完成后再做交接班，避免交接只有空表。Agent 可继续独立咨询，但正式业务接入依赖档案与任务稳定后实施。

## 4. 工作分解

1. 对照现有表、接口、会话协议和权限依赖，设计新业务实体与迁移；避免直接修改历史迁移。
2. 增加工作人员准入、停用和负责老人授权，保留多个管理员账号。
3. 建立老人和床位关联、联系人及照护资料；提供录入、详情、更正与变更轨迹。
4. 将正式照护任务存入 MySQL，定义重复计划实例、执行和异常状态；本地提醒保留为个人便签或明确下线，不静默转成医疗任务。
5. 建立异常处理与交接确认，记录操作者；服务端验证对象、负责人、状态和并发。
6. 接入 Agent 上下文，由服务端组装授权资料，业务草稿和私人聊天分开存储。
7. 将本院制度、公开参考资料纳入版本与审核管理；不把个人健康档案向量化为公共资料。
8. 以真实业务查询替换原型统计，清晰标识演示、无数据、加载失败等状态。

## 5. 技术与目录约定

继续使用 `Yitong Care/frontend` 与 `Yitong Care/backend`。新增模块按老人档案、床位、照护任务、异常、交接班等领域组织，而非为每个页面复制后端流程。

前端在现有 views、components、stores、api 下添加业务模块；后端在 api/v1、schemas、models、services 下分层实现。表变更经 Alembic 新迁移，关键业务约束同时由数据库和服务层保障。最终表名和接口在实施时确认，本轮不创建代码骨架。

主文档在项目根目录的 `项目文档/`，仓库镜像在 `Yitong Care/docs/项目文档/`；本轮同步更新的同名 Markdown 文件保持一致。旧优化记录、评测和架构图是已有系统证据，不改写历史结果。

## 6. 数据迁移和测试数据

保留现有账号、私人会话、知识资料、向量和检索快照。历史无归属测试会话继续按既有显式命令归入指定管理员；多个管理员不自动共享各自私人会话。

新建老人、医嘱和正式任务不得从“张阿姨、健康分86、演示待办”等原型内容自动导入。需要机构演示数据时使用显式样例、虚构身份与演示标志，不覆盖真实记录。

## 7. 质量计划与完成定义

- 权限：普通注册不能获得机构资料；工作人员仅访问授权老人；管理员管理能力和私人会话隔离分别测试。
- 业务：床位冲突、分配变更、重复提交、无法完成、异常关闭、交接接收、历史更正可验证。
- Agent：工作人员与老人身份不混淆；切换老人不串上下文；证据不足、联网失败、模型不可用均明确反馈。
- 数据：审计保留真实操作人；迁移前备份，迁移后核对数据；派生索引可从 MySQL 重建。
- 界面：管理员和工作人员都能看到今日守护与最近对话；只有管理员有知识库与 RAG 管理入口。
- 业务功能完成须同时包含接口、数据库、界面、权限、必要测试、说明文档；只有静态卡片不能标为完成。

阶段验收使用需求编号 NH-*，报告记录环境、案例、结果和限制。现有历史自动测试数量不作为本次新增养老院能力的验收证据。

## 8. 风险与取舍

| 风险 | 处理 |
| --- | --- |
| 角色提前过度拆分 | 本期仅管理员、工作人员；岗位信息与权限分离 |
| 只做页面、缺少实际闭环 | 从档案和数据库任务开始，以跨人员交接验收 |
| AI 建议被当作医嘱或执行记录 | 仅生成草稿，权限人员确认后保存 |
| 老人隐私进入公共知识库或联网 | 业务资料分开保存、授权读取、最小披露 |
| 原型数据混入真实业务 | 保留演示标识，不自动迁移成正式老人数据 |
| 提前开展硬件、家属、多院业务 | 留待后续；部署按用户要求最后补充 |
