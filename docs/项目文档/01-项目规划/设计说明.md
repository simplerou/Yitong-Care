## 1. 产品结构

以老人及照护工作为业务中心，保留六个 Agent 与知识管理能力。账号只分管理员和工作人员两种角色；管理员是一种权限，不是唯一账号，可以多人独立登录。

本期服务单个养老院，老人和家属不直接登录。不额外设计系统管理员、院长、护理主管等子角色；岗位名称可进入员工资料，但不自动改变权限。

## 2. 信息架构（规划）

| 分组 | 页面 | 可见范围 |
| --- | --- | --- |
| 工作台 | 今日任务、异常提醒、最近对话 | 两种角色；展示范围不同 |
| 老人照护 | 老人列表、档案、测量记录、照护记录 | 管理员及有负责关系的工作人员 |
| 照护协作 | 我的任务、异常登记、交接班 | 两种角色；工作人员仅访问授权内容 |
| 智能助手 | 健康、用药、政策、膳食、安全、心理 | 两种角色 |
| 院内管理 | 房间床位、人员、分配、任务计划、异常复核、业务统计 | 管理员 |
| 知识库与 RAG | 文档管理、文本切块、向量入库、检索、检索记录 | 管理员 |

以上新菜单按阶段实施，不一次放出不可用入口。现有“运营服务记录”仍为演示，不能直接改名当作正式照护记录。

## 3. 页面设计

### 3.1 登录与账号

保留独立登录注册界面、密码眼睛图标、可见标签和错误提示。现有账号登录由服务端识别角色，不能通过前端角色选择升级为管理员。

养老院升级后公开注册账号显示待开通提示，管理员开通或审核后成为本院工作人员。已有账号处理方案要在员工准入实现时明确，不能默认任何已注册账号都能读取老人档案。

多个管理员各自使用账号密码，所有管理操作保留本人标识。管理员初始化继续沿用现有本机脚本，不提供公开提权接口。

### 3.2 工作台

工作人员：首页显示本人今日任务、待处理/待交接事项、负责老人入口、最近私人咨询；管理员：首页显示本院任务与异常汇总，并提供院内管理和知识库入口。

“今日守护”和“最近对话”对两种角色均可见。今日守护目标为数据库照护任务，当前浏览器本地提醒只作个人便签，不能假装已接入任务中心。最近对话维持账号隔离，不将管理员演示对话填充给工作人员。

统计必须来自真实业务记录。没有测量、没有任务时显示未记录或空状态，不生成健康分。管理员若查看历史演示内容，持续显示“演示”标签。

### 3.3 老人列表与档案

列表支持姓名、床位和负责范围筛选；顶部显示机构及当前筛选条件。进入档案后固定显示老人姓名、稳定编号、房间床位，敏感信息按权限展示。

档案分基本资料、照护要点、测量、任务、异常、交接及变更轨迹；过敏、吞咽和行动风险用文字和标识共同表达，不能只依赖颜色。允许未知或未记录，不默认填“无”。

更新需要有来源、操作人、时间和更正原因，出生日期与人工填报年龄应区分。老人资料不因 Agent 对话中的一句话自动改写。

### 3.4 任务与异常

任务详情显示对象、负责人、计划时间、执行要求、记录字段和当前状态。完成、无法完成、取消有不同操作和服务端校验；任务详情不提供 Agent 一键自动完成。

测量表单明确单位、时间、输入来源；异常数值或症状提示工作人员按流程处理。风险提示不代表已通知任何人，必须显式上报并生成事件记录。

异常详情分发现情况、处理过程、待办、复核结果；接收和关闭可追踪，重要状态变更需二次核对并避免重复提交。

### 3.5 交接班

提交前展示未完成任务、未关闭异常、观察变化和待跟进事项，可逐条核对。Agent 生成内容显示“待确认草稿”。交班与接班分别操作；提交成功不等于对方已接收。

### 3.6 Agent 界面

进入助手可选“通用咨询”或一个有权访问的老人。老人上下文与登录人员身份分开显示；服务端加载资料，不能依赖客户端自由提交老人 ID 就授予权限。

切换老人应开启对应新会话或显式切换到该老人的既有会话，清空前一位老人的个人条件。聊天框、来源面板持续显示当前对象；模型无权修改其归属。

引用保留原文和来源；机构规程、公开指南、联网参考区分展示。业务草稿带有可编辑区、依据和“确认保存”按钮，保存前再次鉴权并校验版本。

## 4. 技术架构

保留现有前后端分离：Vue 3 + TypeScript + Pinia + Vue Router；FastAPI + Pydantic + SQLAlchemy；MySQL 保存业务和问答快照；LangGraph 编排，Qwen 理解与生成；Embedding + FAISS + BM25 + RRF 检索，Tavily 按需补充官方参考。

新增业务层管理老人、床位、任务、测量、异常、交接及审计，不通过对话日志代替业务表。Agent 服务从业务层读取最小授权上下文，输出建议或草稿，由有权人员通过业务 API 提交。

## 5. 数据关系（目标）

- 机构→空间（楼栋/楼层/房间/床位）；床位分配关联老人并保留历史。
- 账号→角色、员工准入状态；人员与老人之间是有起止时间的负责关系。
- 老人→照护任务、测量、异常、照护记录；每条记录都有实际操作人。
- 任务计划→任务实例→执行记录；异常可由任务或人工观察触发。
- 交接单→交接条目→接收确认；条目引用原任务和异常，不复制覆盖原记录。
- 私人会话→账号，可选关联老人；业务记录的共享不扩大私人会话可见范围。
- 知识文档→资料范围、版本、审核；老人个人档案不是公共知识文档。

本期单院运行，新表预留机构归属；多院跨租户隔离、正式表结构和接口协议仍需后续设计与测试，本文不宣称已经实现。

## 6. 权限与一致性

权限链为登录校验→角色→机构/负责关系→对象→允许操作及状态。所有业务接口在服务端校验，列表过滤不能替代详情和写操作校验。工作人员停用、负责关系变更、老人调床等均需处理现有访问和并发请求。

任务完成、异常关闭、交接接收采用事务与版本检查/等价并发控制；重复请求不得生成重复执行。审计记录包含操作者、对象、时间、动作和变更，不记录密码或明文凭证。

## 7. 知识和数据使用

公共参考与本院制度分范围检索，本院制度未经审核不得作为正式流程依据；废止版本保留历史快照，不悄悄改写已生成引用。外部指南不自动覆盖院内批准流程，发现冲突时明确提示并交管理员核实。

联网请求不包含老人姓名、联系方式、完整病史等个人资料。医疗和危机内容保留现有安全边界；不实现自动诊断、自动开方、自动急救调度或未经确认的业务写入。

## 8. 视觉与交互原则

延续项目政务蓝、温润留白、中文系统字体及既有组件；不因改场景整体推翻界面。桌面提供工作台和表格，移动端优先保障任务查看、登记与上报。可点击控件有明确焦点、足够触达面积；状态包含文字，错误定位到字段。

沿用现有下拉框交互和密码显隐设计。老人切换、任务执行和交接接收优先防误操作；不把内部模型审查字段当作业务提示展示。

## 9. 当前与规划的边界

账号角色、个人会话、六个 Agent 基础流程、RAG、个人本地提醒及真实最近对话已有实现基础。上述房间床位、老人档案、员工准入、正式照护任务、异常工单、交接班和老人上下文属于下一阶段规划。本轮只修改文档，没有新增业务代码或部署配置。
